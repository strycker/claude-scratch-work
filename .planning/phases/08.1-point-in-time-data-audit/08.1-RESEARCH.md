## 2. Where to apply the shift, once

- **The single point** is `transforms_monthly.build_monthly_spine` (lines 319-341), which is the only caller of `macro_monthly.fetch_macro_monthly` and `prices_daily.fetch_universe_prices` (grep-verified). Apply `apply_publication_lags(splice_input, cfg)` **once to `splice_input`** (the concat of macro and monthly_prices) and build *both* the splice and the `monthly_raw` frames from that lagged frame. Today `monthly_raw` re-concats the unlagged `macro` and `monthly_prices` at line 339; change that. Agency columns are added afterwards and never pass through the function.
- **Function:** a new `platform/ingestion/publication_lags.py::apply_publication_lags(frame, cfg)` → `frame[c].shift(L, freq="ME")` per column, with the result reindexed by the caller. `shift(freq=)` moves timestamps rather than positions, so it is safe on gaps. Values past the index end simply wait for the index to grow (verified). It **raises** on any column missing from the table: that is the runtime completeness check.
- **Config:** add a top-level `publication_lags:` map, e.g. `fred_m2sl: 1`, `div_yield: 3`, `fred_gdp: {vintage: true, fallback_months: 3}`. Keep it top-level: `multpl_monthly.datasets` rows are 4-tuples unpacked positionally (macro_monthly.py:211), so they cannot take an inline key.
- **FRED `shift` flag:** every `fred_monthly` entry is `shift: false` today. Delete the keys and the `shift` branch in `_fetch_fred_monthly` (byte-identical output). `apply_publication_lags` raises if any `fred_monthly` entry still says `shift: true`, so a lag can never be applied twice. `fred_daily` (DAAA/DBAA feed the tripwire and never reach `monthly_raw`) is left alone.
- **GDP fallback:** `_shift_fallback_series` gains a `lag` argument, read from the table (`fallback_months`, default 1). The fix is `shift(3)` on the ref-month grid, so ref Jan (Q1) appears at Apr-30. Use a live ALFRED refetch of the agency columns only: FRED is reachable here and `FRED_API_KEY` is set.
- **Consumers that bypass `build_monthly_spine`** all read the *saved* `monthly_raw` and therefore see the lagged data: `evaluation/report.py:830` rebuilds the splice from `monthly_raw`, as do `report/serving.py:190`, `features/invariants.py:45`, `labeling/classifier2.py:67`, `scripts/{run_joint_lift,run_policy_trials,run_subsample_stability,recompute_monthly_features}.py`, and notebooks P1–P6. Only the tripwire (`macro_daily`, `daily_raw`) reads unlagged data, and that is daily market data (lag 0). No consumer calls a fetcher directly.
- **Merge-on-save hazard (Pitfall 1):** `monthly_raw` is in `MERGE_ON_SAVE_CHECKPOINT_NAMES`. `merge_preserving` fills the NaN cells of the new frame from disk (checkpoints.py:110-133). If lagged data is saved over an **unlagged** disk copy, the first L rows of every lagged series go back to their *unlagged* values. The transition needs one `cm.save(..., merge=False)` plus a marker file (`publication_lags.json` recording the applied table, next to `splice_provenance.json`). The build should then refuse to merge onto an unmarked `monthly_raw`.
- **Partial current month (Pitfall 2):** `monthly_index = date_range(start, end=today, "ME")` (transforms_monthly.py:317) **includes the running month when today is its last day** (this is Glenn's 2026-09-30 row). That row mixes multpl's *current price* (the "Sep 29" row wins `.last()`), pre-close daily prints, and lagged series that *are* present, so after lagging it can look "complete". Fix: `end = today.normalize() - MonthEnd(1)`, which gives the last complete month (Sep 30 → Aug 31, Oct 1 → Sep 30; verified).

## Common pitfalls (beyond §2)
- **Returns built from monthly averages (outside the lag scope; flag it for Glenn).** `equities_tr` (sp500 average), `oil` (WTISPLC average) and `long_duration_tr` (GS10 average) produce next-month returns of the form `avg(t+1)/avg(t)`. That return contains the mid-t → end-t move, which the month-end features at t (VIX close, curve close, gold close) have already observed. **Lags do not fix this.** It can flatter the tilt more than the ablation, so D-04's relative answer is at risk. Record it as a caveat in the D-05 sentence and put it on the 8.2 backlog.
- **Before and after must differ only by the lags.** A full network rebuild would also pull new data: 8 more days, and BEA's late-September annual GDP revision (ASSUMED date). The offline migration isolates the lags. The ALFRED refetch changes only pre-1991 GDP; dev values from the vintage era are fixed because they are filtered by as-of.
