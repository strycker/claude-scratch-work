# Phase 8.1: Point-in-Time Data Audit - Context

**Gathered:** 2026-09-30
**Status:** Ready for planning
**Mode:** lean MVP (`.claude/CLAUDE.md`, `REBUILD-FROM-SCRATCH-GUIDE.md` §5). At most 2–3 plans of
about 150 lines each. Mutation proofs are required only for the point-in-time test and the one
decision-bearing number. Decisions go in `platform_design/DECISIONS.md` as rows.

<domain>
## Phase Boundary

This phase delivers three things:

1. **Point-in-time data.** Every raw series enters features only at the month it could have been
   known, and a test enforces this.
2. **One re-measured answer.** On that data, does the regime-tilt strategy beat its no-regime
   ablation over the 1972–2020 walk-forward, net of costs?
3. **Two usability fixes to the weekly report:**
   - it always prints the target allocation;
   - it judges staleness per series rather than against the newest raw row.

**Usable output:** a weekly page that shows a concrete allocation on point-in-time data and runs
reliably month to month. The regime tilt stays unproven unless the re-measurement says otherwise.
The phase ends by recording that answer, so Phase 8.2 can decide whether its MVP gives the regime
view weight or keeps it advisory.

</domain>

<decisions>
## Implementation Decisions

### Trial budget (ADR-0004, declared before any registry-bearing run)
- **Opening count:** `total_trial_count()` = **44**, read live on 2026-09-30.
- **Budget: 2 rows**, one full backtest evaluation of 2 legs:
  - `rows_per_run = 2`: the strategy leg plus the no-regime ablation leg, which are the two
    `append_trial` call sites in `run_full_backtest_evaluation`;
  - `N_runs = 1`.
- **Zero-row components (`NO_REGISTRY`):**
  - the "before" baseline on today's unshifted data (D-06);
  - label-movement diagnostics;
  - serving refits;
  - every test.
- **Phase ceiling: 46.** The DSR hurdle at 46 trials with `sharpe_variance` = 1.0 (still the
  ADR-0002 open-item-8 placeholder) is **2.2442**.
- Going over requires a written amendment *before* the run. Unspent budget expires.

### Publication lags (how)
- **D-01: Measured lag table per series.**
  - Add a `publication_lag_months` entry for **every** raw series in `config/platform_settings.yaml`.
  - Each value comes from the source's own release schedule, conservatively rounded so that the
    value for month m is available by the end of month m + lag.
  - Expected starting points, which the researcher confirms:

    | Series | Lag (months) |
    |---|---|
    | Market prices, yields, VIX | 0 |
    | `fred_m2sl` | 1 |
    | `fred_totalsl` | 2 |
    | multpl `div_yield` | about 3 |
    | `cape_shiller` | to be measured |

  - Lags are applied in ingestion, once, so every downstream consumer sees the shifted series.
    **Reversibility:** costly. Changing a lag changes every feature, label and number after it,
    and invalidates pinned labels and records.
- **D-02: ALFRED stays as is.** The vintage-aligned agency series (`fred_gdp`, `fred_cpi`,
  `fred_unrate`, `fred_indpro`, `fred_payems`) keep their ALFRED handling. The table records them
  as "vintage-aligned" rather than applying a second shift. Do not double-lag.
- **D-03: The point-in-time test fails on a violation.**
  - It fails if any feature at month t depends on a raw value whose publication month exceeds t.
  - It is driven by the lag table plus a synthetic series with a known release date.
  - It must be shown able to fail: remove a lag and the test goes red.
  - This is the phase's one required mutation proof on the data side.

### Re-measurement (what, and what it decides)
- **D-04: Re-run the tilt-vs-ablation question once, on point-in-time data.**
  - Run `run_full_backtest_evaluation` over 1972–2020: regime-tilt strategy plus no-regime
    ablation, L1-driven, 10 bps costs, as configured today.
  - This spends the 2-row budget.
  - Criterion 7 (joint classifier #1 × #2) is **not** re-run; classifier #2 is DEFER in the
    decision register.
- **D-05: What gets recorded.**
  - The walk-forward window;
  - terminal log-wealth and max drawdown for both legs;
  - the delta between them;
  - SPY, 60/40 and Faber for reference;
  - the DSR at the live count.
  - One sentence answering "does the tilt beat the ablation net of costs? yes/no". It is the input
    8.2 needs, and it goes into DECISIONS.md.
- **D-06: The "before" baseline is a zero-row run.**
  - The same evaluation on today's unshifted data runs with `NO_REGISTRY`, so the effect of the
    lags is visible.
  - Before and after are reported side by side.
  - No other re-measurements, amendments or ruling records.

### Weekly report: staleness (behavior)
- **D-07: Staleness is judged per series against its own lag.**
  - A series is stale only if its last value is older than its lag allows at the run date.
  - After the lags are applied, the latest scorable month is the newest month in which every
    model column is present.
  - A partial current-month raw row can no longer trip anything.
- **D-08: Stale data warns; the report still runs.**
  - The report scores the latest month where every series is within its lag.
  - It puts a prominent **STALE** warning at the top naming each late series and how many months
    late it is.
  - This replaces the old "more than 3 month-ends behind the newest row" cap (DECISIONS A-07 is
    superseded by A-12).
  - Still no imputation and no forward-filling.

### Weekly report: target allocation (behavior)
- **D-09: Always print the target allocation as a simple table.** One row per asset class with:
  - class;
  - tradable ticker (SPY / TLT / IAU / USO / cash);
  - target % (the executed book after the no-trade band);
  - last week's %;
  - change.

  It sits at the top of the trades section and prints whether or not any account is configured.
- **D-10: Per-account trades stay optional.** They appear only when a gitignored
  `config/accounts/<name>.yaml` exists and is listed under `report.accounts`. The README gets a
  3-line how-to. Glenn's real holdings are **not** set up in this phase.

### Explicitly deferred (Glenn's default, 2026-09-30)
- **D-11: Deferred to Phase 8.2 or later.** Neither changes the answer to D-04's L1-driven
  tilt-vs-ablation question:
  - **CR-02:** the filtered belief is carried across refits whose state ids are not aligned.
  - **The constant-output L2 nowcaster recipe.**

### Required knock-on (not optional)
- **D-12: Migrate the two test-side hard-coded-44 sites before the D-04 run.** They are
  `tests/unit/test_platform_gate_tiers.py` (`live <= 44`) and
  `tests/unit/test_platform_joint_diagnostics_record.py` (`total_trial_count() == 44`, and
  "08-10's rows are last"). Both break the moment D-04 appends its 2 rows.
  - Keep each **historical** assertion: 08-10 moved the count from 42 to 44 and its rows exist.
  - Check the live count against this phase's declared ceiling of **46** (ADR-0004 § Consequences).

### Claude's Discretion

- Whether `cape_shiller` and `sp500` need a lag. The researcher measures multpl's

<code_context>
## Existing Code Insights

### Reusable Assets
- **FRED ingestion** already supports a per-series `shift` (a 1-period lag) in
  `macro_monthly._fetch_fred_monthly`. Generalise it to N months and extend it to multpl and
  macrotrends.
- **Serving** (`report/serving.py`) and **weekly** (`report/weekly.py`, 08-13/08-14/08-16) already
  score the latest complete month and refuse to impute. D-07/D-08 changes the staleness rule
  there, not the scoring path.
- **`run_full_backtest_evaluation`** already writes both legs and their registry rows.
  `trial_tag` names the run.

### Established Patterns
- Config-driven, with no hardcoded series metadata in Python.
- Parquet checkpoints under `data/checkpoints/platform/`, which are tracked. The rebuild after the
  lag change updates tracked data.
- Fitting uses only data through 2020-12 (dev checkpoint manager).
- Floats are compared at rel 1e-9, abs 0 (H-10).

### Integration Points
- Changing lags changes `monthly_raw`, then `monthly_features`, the L1 labels, returns by regime,
  and serving.
- Pinned records and tests that encode unshifted numbers will move. Update them deliberately and
  list them; don't write amendments for them.

</code_context>
