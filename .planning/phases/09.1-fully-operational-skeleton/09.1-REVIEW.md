## Critical Issues

### CR-01: The STALE assertion depends on the wall clock, so CI turns red on 2026-11-15

**Status:** fixed in `89a89f8` (strycker/trading-crab `claude/phase-9.1-skeleton`): `fixed_build` pins `report.run`'s `run_date` to the fake build's run date.

**File:** `tests/test_report_cli.py:102-112` (assertion at line 112). The clock is read at `src/trading_crab_lib/platform/report.py:101`.

**Issue:** The `fixed_build` fixture pins only the build's `today` (2026-10-14), so the data ends on 2026-09-30.
`main(["weekly"])` then calls `report.run(load())` with `run_date=None`, which renders with the real `date.today()`.
`max_age_days` is 45, so from **2026-11-15** onward the page carries the banner and `assert "STALE" not in page`
fails. The comment ("the fake build's run date is 14 days after its data") is only true today.

I reproduced it: a pytest plugin in the scratchpad set `report.date.today()` to 2026-11-20, and the test then fails.

**Failure scenario:**
- Every CI run on `main` and `claude/**` goes red after 2026-11-14, so no head can meet the D-10 gate.
- Glenn's Mac gate (`pytest tests`) fails the same way if it runs after that date.

**Fix:** Pin the run date in the test so it does not read the clock:
```python
# tests/test_report_cli.py
def test_weekly_puts_the_inverse_vol_mix_on_the_page(tc_root, fixed_build, monkeypatch):
    real_run = report.run
    monkeypatch.setattr(report, "run", lambda cfg: real_run(cfg, run_date=date(2026, 10, 14)))
    ...
```
A second option is a `--run-date` CLI flag, the same seam as `data.end_date`. Also grep the other tests for any
`date.today()` dependence.

## Warnings

### WR-01: Weights are silently a month stale when one ticker's last month-end is missing, while the page says "latest complete month"

**Status:** fixed in `011208d` (tests, red) and `2263c76` (fix): `report.complete_through(raw)` dates the page, the STALE age and the mix; the page names series missing at the latest month-end; `target_weights` raises on a missing last price. Requires human verification (logic change on the decision-bearing mix).

**Files:**
- `src/trading_crab_lib/platform/allocate.py:23-26`
- `src/trading_crab_lib/platform/ingest.py:114,166-167`
- `src/trading_crab_lib/platform/report.py:45,54-58`

**Issue:**
- `target_weights` calls `prices.pct_change(fill_method=None).dropna()`, which drops every row where *any* ticker is NaN,
  then takes the last 36 rows.
- The build has no per-series freshness check: `_usable` only rejects an empty series.
- So when Tiingo returns USO only through August and the other tickers through September, the build succeeds and the
  weights are computed as of August.
- The page still prints `Data through month-end 2026-09-30 (latest complete month)`, since `raw.index.max()` is the
  last row of any column.

I confirmed with a probe that the "stale" weights equal the weights computed on data through August.

Two related problems:
- The "(latest complete month)" text is asserted, not computed. A page rendered on 2026-11-13 from a September build
  says September is the latest complete month, and shows no STALE banner (age 44 ≤ 45, also probed).
- With a 45-day limit, a missed monthly rebuild goes unflagged for up to two weekly runs.

**Failure scenario:** Glenn trades last month's mix by hand while the page claims current data. This is the decision-bearing number.

**Fix:**
1. In `build`, fail loudly (DECISIONS D-08) when any ticker's last valid month-end is earlier than the frame's last
   ticker month-end: `last = {t: raw[t].last_valid_index() for t in tickers}`, and raise `BuildFailed` if they differ.
2. In `target_weights`, raise if `prices.iloc[-1]` has a NaN rather than dropping the row.
3. In `render`, compute the latest complete month-end (`(pd.Timestamp(run_date).to_period("M") - 1).to_timestamp("M")`).
   Show STALE when `through` is earlier, or drop the "(latest complete month)" claim.

### WR-02: `TC_ROOT_DIR` in `.env` (offered by `.env.example`) reads config from one checkout and writes data to another

**Status:** fixed in `b5b8749`: the `TC_ROOT_DIR` line is gone from `.env.example`; the `paths` docstring says `.env` is not read to find the root. Loading behaviour unchanged (README never mentioned it).

**Files:**
- `.env.example:9-10`
- `src/trading_crab_lib/platform/config.py:38,47`
- `src/trading_crab_lib/platform/paths.py:23-25`

**Issue:** `load()` resolves `root()` with the cwd walk, then reads the YAML. Only then does it call
`load_dotenv(root() / ".env")`, which exports `TC_ROOT_DIR` into the process. From then on, every `data_dir()` and
`outputs_dir()` call follows the `.env` value.

A probe confirmed it: with checkout A holding `.env` = `TC_ROOT_DIR=B`, the config is read from A and
`data_dir()` returns `B/data`. `.env` is located through the root it is meant to choose, so the setting cannot work
consistently. It also leaks into pytest `realdata` runs, where `load_dotenv` on the repo's real `.env` mutates
`os.environ` outside monkeypatch.

**Failure scenario:**
- `tradingcrab build` in clone A, run with the config of A, writes `monthly_raw` into clone B.
- The conftest's `BUILT` path (always the repo's own `data/`) then says "no build".

**Fix:** Remove the `TC_ROOT_DIR` line from `.env.example`; it is an exported variable only. In `config.load`, either
load `.env` before resolving the root (from the cwd walk, never re-resolving), or refuse a `.env` that sets
`TC_ROOT_DIR`:
```python
if "TC_ROOT_DIR" in dotenv_values(root() / ".env"):
    raise ConfigError(".env must not set TC_ROOT_DIR: export it in the shell instead")
```

### WR-03: The holdout fence is reachable outside the weekly page: `ingest.build` returns every row, and the guard test only sees literal `True` in `src/`

**Files:**
- `src/trading_crab_lib/platform/ingest.py:15,139,169`
- `tests/test_repo_hygiene.py:135-142`

**Issue:** `build()` returns the full frame, holdout rows included, and its docstring advertises it ("every row;
checkpoints.load gives the dev rows only"). Any development or notebook code that calls `ingest.build(cfg)` gets
2021+ rows without any `include_holdout=True`.

`test_only_the_weekly_page_reads_past_the_holdout` cannot see several other routes:
- `include_holdout=flag`, `include_holdout=1` or `**kw`;
- a direct `pd.read_parquet(data_dir() / "holdout" / ...)`;
- any call in `notebooks/`.

The plan's prohibition ("the default loader cannot return them and only report.py opts into the holdout") is
therefore enforced by convention, not by code.

**Failure scenario:** In 9.4, a tuning notebook does `raw = ingest.build(cfg)` to "get fresh data" and selects on
2021+ rows. No test fails.

**Fix:**
- Make `build` return only what the CLI prints: `(n_rows, through)`, or `checkpoints.load("monthly_raw")` (dev only).
  Update `cli._build` and the `raw` test fixture, which can call `checkpoints.load(..., include_holdout=True)` from
  `tests/` (tests are outside the guard).
- Extend the guard so that any `include_holdout` keyword whose value is not the literal `False`, and any `"holdout"`
  string literal outside `checkpoints.py`, fails.
- Scan the notebook's code cells too.

### WR-04: `clean_workspace.sh` advises `git restore .`, which discards every unstaged edit in the checkout

**Status:** fixed in `d78b473` (tests, red) and `113e9dc` (fix): deleted-before snapshot; fails only on newly missing tracked files and prints `git restore -- <those paths>`.

**File:** `scripts/clean_workspace.sh:23-30`

**Issue:** The script fails whenever `git ls-files --deleted` is non-empty, including files the *user* deleted before
running it. It then prints `Run: git restore .`, which restores every tracked file from the index and silently throws
away all unstaged modifications, not just the missing files.

There is a second gap. The test (`tests/test_repo_hygiene.py:91-102`) runs the script in a temporary tree that is not a
git checkout, so this branch is never exercised. The "never removes a tracked file" claim is checked only after the
`rm -rf`, and never in a test.

**Failure scenario:** Glenn has half-finished edits and has deleted one file on purpose. He runs the script, gets
"tracked files are missing", follows the printed advice, and loses the edits.

**Fix:**
1. Snapshot `git ls-files --deleted` *before* removing anything, and fail only on new entries.
2. Print `git restore -- <those paths>`, never `.`.
3. Add a test that `git init`s the temp tree, tracks a file under `src/`, runs the script and asserts the file survives.

### WR-05: A manual run can publish to real PyPI from any branch, with no version-vs-tag guard

**Status:** docs part fixed in `391a333`: RELEASING §7.3 requires Glenn as reviewer and the `v*`, `lib-v*`, `both-v*` tag rules on `pypi`; §4 updated to match. Workflow unchanged (docs only, as approved).

### WR-06: `checkpoints.save` is not atomic, so a failure mid-save mixes a new dev file with an old holdout and old meta

**File:** `src/trading_crab_lib/platform/checkpoints.py:50-58`

**Issue:** The save happens in three separate steps, in this order:
1. it writes the dev parquet;
2. it writes or unlinks the holdout parquet;
3. it writes the meta.

If the process stops after step 1 (Ctrl-C, disk full, a pyarrow error), the next `weekly` concatenates a fresh dev
file with a stale holdout file. The old meta still passes the lag-table check. This is the D-08 incident class ("a
merge refilled columns from a stale copy") arriving by a different route.

**Fix:**
1. Delete the meta first, so `load_meta` refuses until the save completes.
2. Write each parquet to `NAME.parquet.tmp`, then `os.replace` it into place.
3. Write the meta last.

That is about four lines.

### WR-07: The Mac gate's mix check cannot fail: `Total 100.0%` is true by construction

**Status:** fixed in `577a004` (tests, red) and `5450695` (fix): the Total row is the sum of the rounded rows; tests assert Total == row sum (100.0% kept only where the rows truly sum to it). The realdata 1/vol recomputation was not in the approved scope.

**Files:**
- `tests/test_realdata.py:234`
- `tests/test_notebook.py:200`
- `tests/test_report_cli.py:109`
- `src/trading_crab_lib/platform/report.py:67`
- `src/trading_crab_lib/platform/allocate.py:34`

**Issue:** `cash = max(0, 1 - risky.sum())` with `risky.sum() <= 1` makes `weights.sum()` equal 1 by construction, and
the page prints `100 * weights.sum()`. So `"| Total | 100.0% |"` holds for *any* risky mix: wrong order, a stale row
(WR-01), or a vol target ignored. On real data, that assertion is the only allocation check, so the realdata gate
proves only that the page renders.

The printed total also hides rounding. A probe showed rows of 23.3 / 23.3 / 20.0 / 0.0 / 33.3, which sum to **99.9%**,
under a printed `Total 100.0%`.

**Fix:**
- In `test_realdata.py`, recompute from `report.inputs(load())` and assert three things:
  - the risky weights are proportional to `1 / vol` of the last 36 month-end returns;
  - the scaled sleeve vol is ≤ `vol_target` (rel 1e-6);
  - every ticker's last valid month-end equals `raw.index.max()`.
- On the page, compute the Total row from the rounded rows, or add the note "rows are rounded".

### WR-08: The meta records only the lag table, so a changed holdout cutoff or series map goes undetected

**Files:**
- `src/trading_crab_lib/platform/ingest.py:168`
- `src/trading_crab_lib/platform/report.py:35-36`
- `src/trading_crab_lib/platform/checkpoints.py:63-71`

**Issue:** The dev/holdout split happens once, at save time, with the cutoff in force then. The cutoff is not stored
in the meta, and neither `load()` nor `report.inputs` checks it. If the config cutoff is moved earlier without a
rebuild, `checkpoints.load("monthly_raw")` returns rows past the new cutoff to development code. The notebook's
`assert` catches this; library callers do not.

The same gap covers `fred.series` (for example `gs10: DGS10`), `tickers` and `start_date`: none is checked, so the
page can show data the config no longer describes. The module docstring says it refuses exactly that case.

**Fix:** Write `meta={"publication_lags": lags, "cutoff": cutoff, "fred": cfg["fred"]["series"], "tickers": cfg["tickers"]}`,
and have `report.inputs` compare all four (one dict comparison). Have `checkpoints.load` take `cutoff=` and refuse a
mismatch. Alternatively, `load` reads the cutoff from the meta and re-filters `dev.index <= cutoff`.
