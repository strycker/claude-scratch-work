**Gathered:** 2026-10-12, from Glenn's answers after the 8.5 merge (chat plus three questions).
**Status:** Ready for planning.
**Mode:** lean MVP / walking skeleton (ROADMAP `**Mode:** mvp`). At most 3 plans of about 150 lines each. Decisions

<domain>
## Phase Boundary

Glenn, 2026-10-12, verbatim:

> "I have not been happy with how complex our code has gotten, so we need to also migrate our agent rules and plans
> to the new repo to enforce 'Keep-it-simple-stupid' KISS principles and other decisions we made here. Similarly,
> I haven't been happy with how we've tried to drill down into minute details in this repo rather than build MVP
> modules and 'Death-Star-2-fully-operational' functional skeleton code first. Let's use a lean-startup approach to
> migrating the code, so that we have working modules at each stage of migration and can get to an end-to-end
> series of working notebooks quickest. In other words, I'm more interested in taking our LEARNINGS and
> ARCHITECTURE over to the new repo, rather than just copy code in large batches of files, since that's going to
> persist complex code rather than work from the simplest starting points."

The phase ends when `strycker/trading-crab`:
1. holds no legacy quarterly code, no tracked data and no pickles;
2. carries the rules: CLAUDE.md (KISS first), DECISIONS.md, MODULE-MAP.md, LEARNINGS.md;
3. runs a deliberately naive platform end to end (build → features → weights → weekly page) through `tradingcrab`
   and one end-to-end notebook;
4. has green CI, and both packages build.

**Out of scope:** the full data spine (9.2), the feature taxonomy (9.3), the walk-forward backtest, registry budgets
and DSR (9.4), the full weekly page with tripwire, hysteresis and accounts (9.5), any regime model (9.6–9.8),
publishing to PyPI, and automation.

<decisions>
## Implementation Decisions

### Decision index (the live decisions; details in the sections below)
- **D-01:** `strycker/trading-crab` is the single production repo for both packages. `strycker/trading-crab-lib` gets a pointer README and is archived. `claude-scratch-work` is planning and reference only (G-17).
- **D-02:** The target's legacy quarterly code, tracked data and pickles are removed, not migrated. The platform is rebuilt from scratch, module by module (G-17).
- **D-03:** The package path stays `trading_crab_lib.platform.*`, and the PyPI names stay `trading-crab` and `trading-crab-lib`. Flattening to `trading_crab_lib.*` stays possible later. Nothing is published in 9.1 (G-17).
- **D-04:** `tradingcrab` is the single front door: subcommands such as `build` and `weekly`; the quarterly commands drop out (G-17).
- **D-05:** The rules travel now: CLAUDE.md, DECISIONS.md, MODULE-MAP.md and LEARNINGS.md go into the new repo. GSD `.planning/` stays here until Phase 9 ends (G-18).
- **D-06:** Lean startup: a fully operational skeleton first, every layer present but naive; no bulk copy. Each module is rewritten to the simplest version that meets its gate, using this repo's code as reference only (G-19).

### D-01: One production repo
- Both PyPI pages (trading-crab 0.1.5, trading-crab-lib 0.1.5) already name `strycker/trading-crab`, and its
  `publish-pypi.yml` builds both `.` and `./src/trading_crab_lib`. Keep that layout.
- `strycker/trading-crab-lib` (v0.1.0, stale): Claude pushes a one-line pointer README on a branch; Glenn merges it
  and archives the repo in GitHub settings.
- Work happens on a `claude/` branch in `strycker/trading-crab`; Glenn opens and merges the PRs. The session needs
  push access to that repo (attach it at the start of execution).

### D-02: Clear the target
- Remove `src/trading_crab/{cli,pipeline}.py`, the quarterly modules under `src/trading_crab_lib/`, the root
  `trading_crab`/`trading_crab_lib` entries, `data/`, any tracked parquet/pickle files, the legacy notebooks,
  `scripts/`, `images/` and the Makefile targets that serve the old pipeline.
- Keep: LICENSE, the two `pyproject.toml` files (rewritten), `.github/workflows/ci.yml` (updated), `publish-pypi.yml`.
- Ignore `data/`, `outputs/` and secrets from the first commit (as in 08.5).

### D-03: Packages and paths
- `src/trading_crab_lib/platform/` holds the library code; `src/trading_crab/` holds the CLI.
- Versions get a minor bump (for example 0.2.0) to mark the platform, but nothing is published in 9.1; Glenn
  decides when.

### D-04: The front door
- `tradingcrab build`, `tradingcrab weekly`, plus whatever the skeleton needs (for example `tradingcrab --help`).
  Every command prints its code line first (G-16). The `python -m ...` forms may stay as thin aliases if they cost
  nothing.

### D-05: Rules in the new repo
- **CLAUDE.md**: short. KISS (P-07) first; the honesty rules (locked 2021+ holdout, point-in-time lags, month-end
  P&L, append-only registry once it exists); hard rules (no secrets, no pickles through git, nothing generated
  tracked); code conventions; how to run.
- **DECISIONS.md**: carried over as the live decision log, with rows that only described this repo's history
  trimmed or marked historical. Planner's choice how to do this, as long as it stays one row per decision.
- **MODULE-MAP.md**: M0–M7 interfaces and gates, with "skeleton (naive)" and "target" columns.
- **LEARNINGS.md**: the mistakes not to repeat, one line each, each with the rule that prevents it. Sources: the
  guide's "Learnings from 8.1–8.5", the legacy pitfalls P1–P27, and these phases. Examples: look-ahead through
  centred smoothing; unlagged publication data; monthly-average prices in P&L; record-pin tests tied to tracked
  data; bulk-copied complexity; option and config sprawl; verification layers on non-decision numbers.

### D-06: Lean startup, skeleton first
- Every layer is present but naive. Suggested naive versions; the planner may simplify further:
  - **M1:** a small free-source build: FRED plus month-end prices for the core assets, publication lags from
    config, the 2021+ holdout fence.
  - **M2:** a handful of causal features.
  - **M3/M4:** a simple core mix (fixed or inverse-vol) and the weekly page.
  - **Backtest:** a naive backtest against SPY only if it fits within 3 plans.
- Write each module fresh from the architecture and the learnings. Read the reference code for behaviour and edge
  cases, but do not paste files across.
- Success is measured by working end to end and by readability: Glenn should be able to read the skeleton in one
  sitting.

### Claude's Discretion
- The naive choices inside each layer, file names, the CLI library (argparse is fine), and the notebook layout, all
  within KISS.

  quarterly runner. The `tradingcrab` script points at `trading_crab.cli:run_pipeline`.

  `_config_hash`, the email helpers, and `ingestion.http`, `ingestion.browser` and `ingestion.assets`. A fresh
