<objective>
Fix the root cause of `trading-crab-lib`'s empty PyPI wheel (every published version, including
0.1.4, has shipped zero Python modules), add a CI gate that makes an empty wheel impossible to
publish going forward, bump both packages to the next unburned version (0.1.5), and give the
project PyPI discoverability via README badges.

Purpose: `trading-crab-lib` 0.1.4's published wheel is 4,836 bytes containing exactly four
metadata files and zero of the package's ~100 real Python modules -- `pip install
trading-crab-lib==0.1.4` followed by `import trading_crab_lib` raises `ModuleNotFoundError`. This
is not new: 0.1.3 was equally empty. Because `trading-crab` pins `trading-crab-lib>=0.1.4`, the
app's `tradingcrab` CLI is broken too when installed from PyPI. Root cause: `src/trading_crab_lib/`
is simultaneously the project directory (where `pyproject.toml` lives) and the package's own
content directory (a flat layout) -- `[tool.setuptools.packages.find] where = [".."]` was written
to paper over this by re-discovering the package one level up, but modern setuptools refuses to
let `where` escape the project root and silently returns an empty package list instead of
erroring. Neither `twine check --strict` (validates metadata, not contents) nor the existing
`build-pkg` job in `python-package.yml` (only proves `python -m build` exits 0, never inspects the
artifact) can detect this class of defect -- exactly the kind of evidence-that-cannot-detect-a-
wrong-value already catalogued in `.planning/UAT-AUDIT-2026-09-09.md`.

Output: `src/trading_crab_lib/pyproject.toml` fixed to actually package the library; a new
install-and-import smoke-test gate in `.github/workflows/publish-pypi.yml`; both packages bumped
to 0.1.5 at every live-pin site; PyPI badges in `README.md`; and a new section in
`docs/RELEASING.md` recording the trap and how to check a wheel's contents by hand.
</objective>
